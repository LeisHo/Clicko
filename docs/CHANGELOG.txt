2026-08-27 | Debounced duplicate pointerdown events - fixes "a single click sometimes logs as 2" | User: fast clicking sometimes registered one physical press as 2 taps. Most likely cause: mouse/trackpad switch "bounce" (a worn or cheap switch sending 2 electrical down-signals for 1 physical press, a well-known hardware phenomenon) or an occasional duplicate pointerdown from the browser - neither is a code logic bug, both are genuine duplicate events arriving a few ms apart. Added a 50ms debounce: a pointerdown within 50ms of the last ACCEPTED one is ignored outright (no real intentional 2nd tap is ever that fast; only bounce/duplicate events are). Reset alongside the other per-round state so it can't carry over between rounds. Verified: 2 pointerdown events dispatched synchronously back-to-back (genuinely 0ms apart, a closer proxy for real switch bounce than a throttled setTimeout, which this test tool's tab throttling inflated from a requested 5ms to an actual 350ms on the first attempt) -> counted as exactly 1 tap; 5 taps spaced a real 300ms apart -> all 5 counted normally, confirming the debounce doesn't interfere with legitimate gameplay.

2026-08-27 | CORE SEMANTICS CORRECTION: the timing value is a MAXIMUM gap between taps, not a minimum floor -- root cause of every prior "win/lose doesn't work" report this session | User gave 3 precise repro scenarios (stop early = nothing happens when it should lose; hit exact target = nothing happens when it should win; overshoot = nothing happens when it should lose) plus an explicit correction: "minimum time means maximum time... there is a maximum time, which is the top margin of how much time is allowed between each click." This is the actual root cause of every timing bug chased this session -- from the very start, the "minimum time between taps" reading of the original spec was implemented as a FLOOR (reject taps arriving faster than the value, silently, no penalty), when it should have been a CEILING (a maximum allowed gap; no floor at all, tap as fast as you want). That floor logic silently dropped most of a normal player's real taps whenever they tapped faster than the current value, so the internal counter could get permanently stuck under the target no matter how many times they physically pressed -- exactly matching "I clicked the right amount of times... nothing happens" and "I clicked more than enough... nothing happens" (both undercounted internally). Rebuilt the mechanic to the user's literal 3-part spec: every tap counts immediately, no speed floor; an overshoot (count > target) ends the round in an instant loss; every tap (whether under, at, or count-wise irrelevant to the target) reschedules a single maxTimeMs countdown, and if no further tap arrives before it fires, the round resolves immediately based on whatever the count is then (win if exactly target, lose otherwise) -- this also fixes the "stop early, nothing happens" report, since the prior version (this same session, 2 commits ago) had removed all timing checks for taps below the target based on a since-corrected reading of an earlier, less precise description. Renamed minSpeedMs -> maxTimeMs and relabeled the dev panel/on-screen display ("Starting Speed" -> "Starting Max Time (ms)", "Speed Display (min ms)" -> "Speed Display (max ms between taps)") so the code and UI can no longer silently drift from the corrected semantics the way the old naming did. Verified via 3 dispatched-PointerEvent tests matching the user's own 3 reported scenarios exactly: 3 taps against target=8 then a 600ms pause -> "DIDN'T MAKE IT! (3/8)" (was previously silent); 5 fast taps (60ms apart) against target=5 -> "NICE!" (was previously silent, since the taps would have been rejected as "too fast" under the old floor logic); 7 taps against target=4 -> instant "ONE TOO FAR! (5/4)" the moment the 5th tap registered.

2026-08-27 | Win/loss mechanic rebuilt from scratch to match the user's exact description, replacing the whole "auto-check after every tap" model | User: "the winning still doesnt work... theres a score counter, so when the score counter hits the right number, you start counting and if he doesnt press anything by the time the minimum time has passed, he wins. if he does hit it again, then immediately tell him he lost... I dont want to have to wait for the round to end." Follow-up clarifying the ORIGINAL symptom: "i tapped the button the correct amount of times, but nothing happened, then i waited for 2 seconds, then it told me i lost" -- a correct exact-match tap sequence resolving to a LOSS after a delay, not a premature loss. Root cause: every previous version of this mechanic (including this same session's earlier stopGraceMs fix) scheduled a generic pass/fail check after EVERY tap, comparing count to target only when that timer fired later -- any code path or timing edge in that shared generic check could in principle resolve an exact match to endGame(false) instead of endGame(true), and there was no structural guarantee against it. Rebuilt entirely: taps below the target now carry NO timer at all (pause as long as you want between them, only the min-gap floor applies when a tap does happen); reaching the target starts a dedicated win-only countdown whose callback can ONLY ever call endGame(true) or do nothing -- there is no code path left, anywhere, that can produce a delayed loss for an exact-match sequence. Once the target is reached, ANY further tap (even one fast enough that it would normally be ignored pre-target) ends the round in an immediate loss with zero wait, matching "I dont want to have to wait." Removed the now-fully-unused Stop-Tap Grace slider/state. Verified via 3 dispatched-PointerEvent tests: (1) reach target, wait past minSpeedMs with no more taps -> win ("YES!"), (2) reach target, tap again after only 50ms -> instant loss ("ONE TOO FAR! (3/3)", ~1075ms total elapsed, no waiting), (3) tap some taps, pause 3s mid-sequence (well past the old grace window), resume and reach target -> win ("FANTASTIC!"), confirming pausing before the target is no longer penalized at all.

2026-08-27 | Unified mouse+touch input to Pointer Events (eliminates a possible double-tap-count path); loss messages now say why and show the actual count | User reported "still not working" (correct tap count still rejected) after the prior round's fixes -- re-audited the input layer rather than re-trusting the earlier timing fix alone: gameButton/startButton each had BOTH mousedown/mouseup/mouseleave AND touchstart/touchend listeners attached simultaneously, relying on preventDefault() to fully suppress the synthetic mouse events a real touch fires afterward. Replaced both elements' separate mouse+touch listener pairs with unified pointerdown/pointerup/pointercancel/pointerleave (Pointer Events merge mouse/touch/pen into one stream with no synthetic-event duplication by design). Verified via dispatched PointerEvents: 5 rapid taps against a target of 3 correctly stopped counting at exactly 4 (immediate overshoot-loss, no double-count), a 3-tap/5-target timeout case correctly landed on exactly 3 | Loss messages: split the single generic pool into 'too many' (TOO MANY!/OVERSHOT!/TOO FAR!/etc) and 'not enough' (TOO SLOW!/NOT ENOUGH!/RAN OUT OF TIME!/etc) pools selected by the actual failure cause, and appended the real (count/target) to every loss message -- e.g. "TOO FAR! (4/3)" -- both to directly answer the user's ask and to make any future report immediately diagnosable from the screen itself rather than needing a live debugging session.
